Normal classes flow straight through. The waiting room and seat holds engage automatically only when demand for one event spikes.

Why a registration layer in front of Salesforce

  • Thousands of people grabbing the same 30 seats means thousands of writes to the same event record at once. Salesforce locks that record during each write, so a direct surge causes queuing, timeouts and "unable to lock row" errors.
  • Salesforce also caps concurrent and daily API calls. The buffer turns a spike into a steady stream Salesforce handles comfortably.
  • Recommended build: Heroku (Salesforce's own cloud) with Redis for seat counts and a durable queue. MuleSoft or AWS also fit if Memorial Hermann prefers them to confirm.

Registration inside the existing My Memorial Hermann app

We add a Classes and Events entry to the app people already have. We do not build or publish a new app. The app is built on Epic MyChart, so how it is added depends on what Memorial Hermann's Epic team can configure. Lucky Rai's team owns this.

Option A: app menu link start here

A menu activity opens our mobile-optimized registration page inside the app. Same flow as the website. Lowest Epic effort; can go live with Phase 1.

Sign-in: the registrant confirms name, email and phone on the page. No patient record is read.

Option B: SMART on FHIR launch

The app launches registration with the signed-in patient's identity, so name and contact details are pre-filled and the registration links to the right person automatically.

Needs Epic app registration and launch configuration to confirm.

What the app channel adds

  • One registration flow and one data model for website and app, so nothing is built twice.
  • Confirmation shows the QR check-in code and an "Add to calendar" action in the app.
  • Reminders go by SMS and email. In-app push or MyChart messages are used only where Epic supports them to confirm.
  • Emails, texts and posters carry deep links that open the app if installed and the website if not.

High-demand events: 100,000 clicks, 30 seats

The goal is not only to stop the system from breaking. Every person who clicks gets a clear answer within seconds, nobody pays for a seat they did not get, and nobody who showed interest is lost.

Seat holds are atomic, so two people can never get the same seat. Holds that are not paid within 10 minutes go back to the pool.

How each step works

StepDesign
Absorb the click floodEvent pages are cached at the CDN, so browsing costs Salesforce nothing. WAF rules, bot detection and per-device rate limits stop scripts and repeat clicking.
Fair admissionWhen visitors for one event pass a threshold, a virtual waiting room switches on automatically and admits people in arrival order at a rate the backend can handle. Candidates: Queue-it or Cloudflare Waiting Room to confirm.
Seat holdsEach admitted person gets a seat hold from an atomic counter (no race conditions). Holds last 10 minutes. Paid holds become registrations; expired or failed ones return to the pool instantly.
Write to SalesforceConfirmed registrations go through a durable queue with an idempotency key, so retries never create duplicates and a Salesforce slowdown never loses a registration.
Sold outOne tap to join the waitlist (ordered, with a position) or the interest list ("tell me when there is a new date"). Both capture contact details and consent.
Waitlist promotionWhen a seat frees up (cancellation, no payment), the next person gets an SMS and email offer with a 2-hour claim window, then it moves on automatically.

Turning overflow into more sessions

For each event we track a demand ratio: (waitlist + interest list) ÷ seats. When it passes a threshold, for example 3×, the system:

  1. Alerts the event owner with the numbers and a recommendation: add a date, a bigger room, or a virtual session.
  2. Lets staff clone the session in one click.
  3. Offers the new seats to the waitlist first, then announces them to the interest list through Marketing Cloud.

In the future state, the Demand Agent (section 11) does this analysis and drafts the new session for staff approval.

Payments and data security

Card data never enters our systems

sequenceDiagram
  actor P as Registrant browser or app
  participant R as Registration service
  participant G as Chase hosted page
  participant SF as Salesforce
  R->>G: Create payment session (amount, reference)
  G-->>R: Session token
  R-->>P: Open hosted payment page
  P->>G: Card details typed directly into gateway page
  G-->>P: Approved
  G->>R: Signed webhook (token, last 4 digits, auth code)
  R->>R: Verify signature, idempotency check
  R->>SF: Payment record: token reference, last 4, amount, status
  Note over SF: No card number, CVV or expiry is ever stored
  • Card numbers go from the registrant straight to the gateway's hosted page. Salesforce stores only a token reference, last 4 digits, amount and status.
  • This keeps Memorial Hermann's PCI DSS scope to the simplest level (SAQ A for hosted pages) to confirm with MH finance.
  • Refunds use the stored token through the gateway API. Webhooks are signature-verified and idempotent. A daily job reconciles gateway settlements against Salesforce.

Registrant and patient data

A class topic can reveal a health condition (for example a diabetes support group), so registration data is treated as sensitive even when the person is not known to be a patient.

DataExamplesProtection
PublicEvent titles, dates, locationsCached at the CDN; no personal data
Personal (PII)Name, email, phone, addressEncrypted at rest and in transit; field-level security; least-privilege access
SensitiveClass topic, caregiver relationship, survey answers, CME recordsShield Platform Encryption on selected fields; restricted permission sets; access logged
PaymentToken, last 4 digits, amountNo card data stored; token usable only through the gateway
ConsentPer-channel opt-in, preferencesCaptured at registration; synced to Marketing Cloud; enforced before every marketing send

Security controls

Platform

  • TLS 1.2+ everywhere; encryption at rest
  • Salesforce Shield: Platform Encryption, Event Monitoring, Field Audit Trail
  • Business Associate Agreement coverage for Health Cloud and Marketing Cloud to confirm
  • Backups with tested restores; masked data in sandboxes (Data Mask)

Access and application

  • SSO with MFA for all staff; least-privilege permission sets
  • No third-party tracking pixels on registration or payment pages
  • Bot defense, rate limits and CAPTCHA on high-demand events
  • Secure code review, dependency scanning, penetration test before go-live

Reliability: what happens when something fails

FailureWhat registrants seeWhat the system does
Payment gateway slow or downSeat stays held; "finish payment" link by emailRetries with backoff; extends the hold once; alerts the on-call team
Salesforce maintenance or slowdownNothing; registration still confirmsQueue buffers writes and replays them in order; dead-letter queue with alert for anything that cannot be written
Marketing Cloud delayConfirmation may arrive a few minutes lateTransactional sends prioritized; confirmation page already shows the QR code
Double clicks or repeated submitsOne registration, one chargeIdempotency keys on every registration and payment
Virtual meeting link failsBackup link sent automaticallyHealth check on links before the event; fallback room
Traffic far beyond forecastWaiting room with honest wait timeAdmission rate tuned live; core registration protected

Running it

  • Monitoring: live dashboard for traffic, seat holds, payments, queue depth and message sends; synthetic tests run the registration flow every few minutes.
  • Alerting and runbooks for every failure above; named on-call during big launches.
  • Releases through CI/CD with automated tests and feature flags; load test before every major conference opens.
